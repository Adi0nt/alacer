# Benchmarks

Java 25 is now the primary benchmark runtime. Fresh controls and verification are in
[the Java 25 migration archive](benchmarks/2026-10-20-java25/README.md), with compatibility
details in [JAVA25.md](JAVA25.md). The Java 8 measurements below and every 2026-10-19 archive
are historical references, retained unchanged. Their GC/runtime and bytecode differ from
the Java 25 series; do not pool them or use them to automatically select defaults.

All numbers here come from the mod's scripted benchmark (see the README) and were measured on
one machine. They show the direction and rough size of an effect, not a guarantee for other
hardware. Raw summaries are archived next to this file; raw per-frame CSVs stay in
`run/alacer/benchmarks/` (not committed).

## Method

- Each variant runs in a fresh JVM. Variants alternate (off, on, off, on) so slow drift such
  as thermals or background load affects both equally. Runs of the same variant are pooled.
- The world was generated by earlier, discarded runs, so no phase includes world generation.
  The integrated server still runs in the same process, as in normal singleplayer.
- Phases: `static` 10 s, `pan` 15 s (two full turns), `fly` 20 s at 20 blocks/s. Before each
  phase the runner waits until no chunk builds are pending for 2 s (`static` also waits at
  least 10 s after joining).
- Frame time is measured start to start of `Minecraft.runGame()`. Allocation is the client
  thread's own allocated bytes per frame (HotSpot per-thread counter); other threads are not
  included.
- Noise floor: in the `static` phase, where the optimization has nothing to do, same-variant
  runs differed by up to about 7% in average FPS (814 to 879). Treat smaller differences as noise.

## 2026-10-19 (session 2) — validation, entity rendering, lookup cache

Same machine and settings as above. Raw summaries for every run and the generated comparison
tables are in [benchmarks/2026-10-19-entities-and-validation/](benchmarks/2026-10-19-entities-and-validation/).

### Methodology changes

- **Fresh world per run.** Each run plays a copy of the base world (`alacer-benchmark-run`), so
  spawned mobs and chests never leak into later runs.
- **Entity density.** `alacer.benchmark.entities=N` places N NoAI pigs, cows, sheep and wolves
  (no chickens: they lay eggs, which adds entities over time) on a 2-block grid around the
  camera. The base world itself has 9 worldgen animals near the anchor.
- **Search-only and per-phase CPU timing.** A `visibility` section times only the search, in
  both modes. Client-thread and process CPU time are sampled per phase.
- **Driver threading mode dominates separate-launch variance with entities.** Separate launches
  of the *same* configuration land in one of two driver modes:

  | Mode (same config) | process CPU | swap | `entities` (1000 mobs, static) |
  |---|---:|---:|---:|
  | Single-threaded | 1.1-1.3 cores | 0.2-0.35 ms | 2.2-3.2 ms |
  | Threaded | 1.8-2.1 cores | 0.03-0.04 ms | 0.86 ms |

  The mode can even switch mid-run. Entity drawing is mostly OpenGL calls, so its cost differs
  several-fold between modes. That swamps a 0.05 ms effect: separate-launch A/B at 200 and 1000
  mobs gave contradictory results (for example vanilla at 1000 mobs measured 3.19 ms in one run
  and 0.86 ms in another). The fix is **in-process A/B** (`alacer.benchmark.toggle=<option>`):
  static and pan run as segments A, B, B, A in one launch, flipping the option between
  segments, so both variants share driver mode and JIT state. Separate launches are still
  used where variance is low (0 mobs).
- **Warm-up segment.** In the first in-process runs the first pan segment (`pan-a1`) was always
  slowest (process CPU 1.4-1.6 vs 1.1 cores): the first turn reveals chunks the static view
  never compiled. That penalizes A, so pan numbers below exclude `pan-a1` and compare `pan-a2`
  against `pan-b1`+`pan-b2`. The runner now records an unscored `pan-warmup` turn first.

## 2026-10-19 (session 3) — rate-limited GL error checks (`render.throttleGlErrorChecks`)

Same machine and settings. Raw summaries and the generated tables are in
[benchmarks/2026-10-19-gl-error-checks/](benchmarks/2026-10-19-gl-error-checks/).

**Machine state.** Baseline frame times this session were about 1.5-2x those of the morning
sessions in the same configuration (200 mobs, static: 2.9 ms vs 1.5-1.7 ms; swap 0.37-0.6 ms
vs 0.18-0.22 ms). The GPU showed about 37% utilization from other desktop applications while
the game was not running. Absolute numbers below are therefore not comparable with earlier
sections; the in-process A/B differences are.

### Correctness

`render.throttleGlErrorChecks.verify=true` (throttling on) raises a harmless `GL_INVALID_ENUM`
(`glEnable` of an invalid capability) in a skipped frame and checks that the next check
reports it. One full benchmark run (200 mobs, about 70 s): **68 errors injected, 68 reported,
0 missed**, each in vanilla's three-line format with the added note. Delays were about 1 s
(the check interval), except one reported 614 ms after injection by the guard described next.

**Found during verification: LWJGL throws on a pending error.** The first verify run crashed
with `OpenGLException: Invalid enum (1280)` in `Display.setVSyncEnabled`. LWJGL 2 calls
`glGetError` and throws whenever the swap interval is set (`Display.setVSyncEnabled`, and
internally when the display is created or its mode or fullscreen state changes). With vanilla's
every-frame checks an error is normally read before that can happen; with throttled checks it
can still be pending. Vanilla changes these at runtime in the vsync option (an uncaught
exception: crash) and in `toggleFullscreen` (caught: the toggle fails). Both call sites, and the
benchmark's own vsync change, now read pending errors first. In addition, after the first real
error is reported, checks return to every frame for the rest of the session. The guard ran once
in the verify run above (at the benchmark's vsync change). The fallback was reviewed but not
exercised in-game.

### Interpretation and decision

In single-threaded mode `glGetError` is nearly free, so rate-limiting it neither helps nor
hurts. In threaded mode each check makes the client thread wait for the driver thread; skipping
it mostly shifts that wait to the next synchronizing call, leaving a saving of about 2-3% of the
frame. Error reporting is verified (above), and the guard and fallback keep LWJGL's own error
checks from failing. **The option is on by default.** It can be turned off with
`render.throttleGlErrorChecks=false` for exact per-frame error locations.

### Benchmark watchdog

Nothing bounded a launch whose client thread hangs: the stage timeouts (world load 180 s,
population 30 s, settle 90 s per segment) only run while frames do, and the settle limits alone
